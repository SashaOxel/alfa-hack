# Модели

Всё в этом документе — зона Python: обучение офлайн (`ml/packages/training`), инференс в `ml_service`. Как результаты моделей превращаются в офферы и решения — в [offer-engine.md](offer-engine.md) (Go).

| # | Модель | Зачем | Алгоритм | Приор. | Владелец |
|---|---|---|---|---|---|
| 1 | Категоризация транзакций | Выручка vs займы, скрытые долги, ФОТ, налоги | Правила + TF-IDF (char n-grams) + LogReg | P0 | ML-1 |
| 2 | PD (вероятность дефолта) | Риск-грейд, ставка, лимит, «здоровье» | CatBoost + isotonic-калибровка | P0 | ML-2 |
| 3 | Вероятность одобрения | «Вероятность одобрения 78%», what-if | LogReg поверх PD и параметров заявки | P0 | ML-2 |

## 1. Категоризация транзакций

**Вход:** назначение платежа, имя и ИНН контрагента, направление, сумма, канал.

**Каскад:**
1. **Справочник контрагентов** по ИНН (`counterparty_registry`): маркетплейсы → `revenue_marketplace`, банки-эквайеры → `revenue_acquiring`, МФО → `mfo`, лизинговые → `leasing`, УФК / ФНС → `revenue_gov` / `taxes`. Это покрывает большую часть объёма.
2. **Правила по назначению** (регулярки): «заработная плата|аванс» → `payroll`, «погашение (основного долга|кредита)|проценты по кредиту» → `debt_service`, «аренд» → `rent`, «ЕНП|единый налоговый» → `taxes`.
3. **ML для остатка:** TF-IDF по символьным n-граммам назначения + имя контрагента + признаки суммы → LogisticRegression. Метки — `category_true` из синтетики.

**Метрики:** macro-F1 на отложенных клиентах (по клиентам, не по транзакциям). Цель ≥ 0,9 (синтетика), отдельно recall для `debt_service` и `mfo` — от них зависит обнаружение скрытых долгов.

**Где используется:** офлайн в `datagen` при загрузке (проставляет `bank.transactions.category`) и онлайн через `Categorize` для новых транзакций.

## 2. PD-модель

| | |
|---|---|
| Таргет | `default_12m` (синтетический, [data-generation.md](data-generation.md#5-метки-для-обучения)) |
| Признаки | [features.md](features.md), с NaN для отсутствующих источников |
| Аугментация по источникам | Каждый клиент попадает в обучение несколько раз с **разными масками источников** (только Tier 0; Tier 0–1; Tier 0–2; всё). Модель учится работать на любом подмножестве данных, и подключение источника честно меняет скор |
| Алгоритм | `CatBoostClassifier(depth=6, iterations≈1000, learning_rate≈0.05, auto_class_weights=None, cat_features=[…])`, early stopping |
| Валидация | Out-of-time: обучение на `as_of` до T−6 мес, тест на последних. Плюс разбиение по клиентам |
| Калибровка | Isotonic на отложенной выборке |
| Метрики | ROC-AUC / Gini, Brier score, калибровочная кривая, Gini по Tier-маскам |
| Грейды | По калиброванному PD: A < 1%, B < 2,5%, C < 5%, D < 10%, E ≥ 10% (пороги в `artifacts/pd/<v>/grades.yaml`) |
| Health score 0–1000 | Монотонное отображение: `1000 × (1 − rank_percentile(PD))`, сглаженное. На главной — «Финансовое здоровье 814» |

**Проверка, что модель учит правду** (слайд для жюри): генератор знает истинные веса скрытых факторов. Сравниваем SHAP-важности признаков-прокси с этими весами и показываем, что модель восстановила зависимость.

## 3. Вероятность одобрения

Approval зависит не только от клиента, но и от запроса: 2 млн и 5 млн для одной кофейни — разные шансы.

```
approval_prob = σ( b0 + b1·logit(PD) + b2·(payment / FCF) + b3·(amount / affordable_limit)
                   + b4·product_kind + b5·stop_soft_flags )
```

- Обучается на синтетических заявках, размеченных синтетической политикой андеррайтинга + шум ([data-generation.md](data-generation.md#5-метки-для-обучения)).
- `monthly_payment_kop` и `limit_kop` в сценарии считает **Go** (калькулятор и движок лимитов). Python не знает ставок и формул продуктов, он получает готовые числа.
- Батч: Go шлёт 5–15 сценариев за раз (продукты × what-if), ответ < 100 мс.

## 4. Объяснения (SHAP)

- `model.get_feature_importance(type="ShapValues")` по сценарию → вклад каждого признака в logit PD.
- В ответе топ-10 по `|shap|`: `{feature, value, shap}`.
- Go превращает их в фразы через `config/feature_texts.yaml` ([features.md](features.md#тексты-для-объяснений)) и показывает 3–5 главных со знаком.
- Для approval-модели (линейной) вклад параметров заявки считается напрямую: `b_i · x_i`.

## Контрфакты («как повысить шанс»)

Python **не ищет** контрфакты сам: он только скорит сценарии. Go строит управляемые сценарии ([offer-engine.md](offer-engine.md#8-what-if-и-как-повысить-шанс)):

| Рычаг | Как задаётся в `Scenario` |
|---|---|
| Уменьшить сумму / увеличить срок | `amount_kop`, `term_months`, пересчитанный Go `monthly_payment_kop` |
| Погасить недоимку / долг ФССП / закрыть МФО | `assume.tax_debt_repaid`, `fssp_repaid`, `mfo_closed` → Python обнуляет соответствующие признаки |
| Подключить источник | `assume.assume_sources=["ofd"]` → Python подставляет **априорные** значения (модель 6) |
| Зонтичное поручительство | Go уменьшает необеспеченную часть, `limit_kop` растёт |

## 5. Прогноз денежного потока

**Задача:** на 30–60 дней вперёд дать остаток (p10 / p50 / p90) и список ожидаемых крупных платежей. Детекция разрыва и подбор овердрафта — в Go ([offer-engine.md](offer-engine.md#кассовый-разрыв--овердрафт)).

**Подход (интерпретируемый, достаточный для хакатона):**

1. **Регулярные платежи** (детекция на истории 6–12 мес): группировка списаний по (категория, контрагент), поиск периодичности (14 / 30 / 90 дней) по автокорреляции дат, медиана суммы. Результат: аренда 1-го, ЗП 5-го и 20-го, ЕНП 28-го, квартальная закупка зерна, платежи по кредитам. Налоги по календарю режима добавляются правилами (УСН — авансы по кварталам).
2. **Выручка:** `base_level × season[month] × weekday[dow] × trend`. Профили оцениваются по истории клиента, а при истории < 12 мес смешиваются с профилем архетипа ОКВЭД. Альтернатива для сравнения — `statsforecast` (MSTL / AutoETS).
3. **Нерегулярные списания:** средний дневной уровень по категориям (поставщики пропорционально выручке).
4. **Остаток:** `balance[t] = balance[t−1] + inflow[t] − outflow[t]`.
5. **Неопределённость:** бутстреп остатков дневной выручки (200 траекторий) → квантили p10 / p50 / p90.

**Бэктест:** скользящее окно на последних 90 днях истории, метрика WAPE по дневному потоку и ошибка минимального остатка в горизонте. Возвращаем `backtest_wape` для режима прозрачности.

## 6. Априорные значения источников

Чтобы показать «подключите ОФД → до +600 000 ₽», **не читая данные ОФД клиента** (согласия ещё нет):

- Для каждого источника и архетипа ОКВЭД обучаем условные распределения его признаков от наблюдаемых Tier 0–1 признаков (квантильная регрессия или медианы по бинам). Пример: `ofd_revenue_to_bank_revenue | okved=56.30, share_acquiring=0.85` → медиана 1,12 (наличные ~12%).
- В сценарии `assume_sources` Python подставляет **медиану** как значение признака и скорит.
- Go показывает результат с формулировкой «до» и «ожидаемо». После реального согласия считается по настоящим данным.

## Артефакты и версии

```
ml/artifacts/
├── categorizer/1.0.0/{model.joblib, vocab.json, metrics.json, MODEL_CARD.md}
├── pd/1.0.0/{model.cbm, calibrator.joblib, grades.yaml, feature_spec.json, metrics.json, MODEL_CARD.md}

├── priors/1.0.0/{priors.parquet}
└── forecast/1.0.0/{archetype_profiles.json, params.yaml}
```

- `feature_spec.json` — список и порядок признаков + версия бандла. `ml_service` при старте проверяет совместимость и падает с понятной ошибкой, если версии не сходятся.
- `MODEL_CARD.md`: данные, метрики, ограничения («обучено на синтетике»), дата, автор.
- Каталог `artifacts/` в git не коммитим. Для демо — архив в релизе или общая папка. `make train` воспроизводит его из синтетики за минуты.

## Что честно говорим жюри

1. Модели обучены на синтетике: мы показываем **работающий пайплайн и объяснимость**, а не качество на реальных данных.
2. Генератор устроен так, что можно проверить, восстанавливает ли модель заложенную зависимость. Восстанавливает (показываем).
3. Реальные данные подключаются адаптером ([ADR-0006](../03-architecture/adr/0006-canonical-data-and-adapters.md)), обучение перезапускается той же командой.
4. Решение по кредиту принимают модель и правила, LLM только объясняет ([ADR-0007](../03-architecture/adr/0007-scoring-catboost-shap.md)).
